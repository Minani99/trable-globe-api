# 성능 점검 — 2026-11-16

## 결론

사이트가 느린 주된 이유는 코드의 비효율이 아니라 **요청 구조와 무료 플랜 인프라의 조합**입니다.
백엔드 쿼리 수는 요청당 2~10개로 과하지 않았습니다. 그런데 모든 페이지 조회가 캐시 없이
Vercel → Render(무료, 0.1 CPU) → Neon(무료, 5분 뒤 절전)을 3~5번씩 왕복하고 있었습니다.

이번에 코드로 고칠 수 있는 세 가지를 반영했습니다.

## 측정 방법과 한계

- 운영 서버(`onrender.com`)는 이 작업 환경의 네트워크 정책으로 막혀 있어 직접 재지 못했습니다.
- 로컬 백엔드(H2)에서 요청별 SQL 수를 세었습니다.
- Next와 백엔드 사이에 요청마다 300ms를 더하는 지연 프록시를 두고, 프로덕션 빌드로 페이지 응답 시간과 백엔드 호출 수를 쟀습니다. 300ms는 원격 API와 DB 왕복을 흉내 낸 가정값입니다.
- 따라서 아래 숫자는 **상대 비교**용입니다. 실제 운영 수치는 리전과 절전 상태에 따라 달라집니다.

## 원인 분석

| 원인 | 근거 |
| --- | --- |
| 공개 데이터를 전혀 캐시하지 않음 | `apiGet`이 `cache: "no-store"`. 프로필 한 번 조회에 백엔드 4회, 여행 상세 2회 호출 |
| 랜딩의 샘플 지구본이 방문자마다 백엔드를 호출 | 브라우저 → `/api/profiles/*` rewrite → Render로 3회 직행 |
| DB 커넥션이 60초 만에 모두 닫힘 | `minimum-idle: 0`, `idle-timeout: 60s`. 1분 쉬었다 누르면 동시에 나가는 3~5개 요청이 각각 TLS·인증 핸드셰이크를 새로 함 |
| 응답 압축 없음 | 여행 목록 45KB, 국가 12KB가 그대로 전송 |
| 무료 플랜의 콜드 스타트 | Render 절전(15분), Neon 절전(5분). 코드로는 완화만 가능 |

백엔드 쿼리 수(로컬 측정): 프로필 4, 국가 2, 여행 목록 3, 여행 상세 3, 추천 9~10, `auth/me` 2.
N+1 문제는 없었습니다(`default_batch_fetch_size: 50`, `open-in-view: false`).

## 반영한 변경

### 1. 공개 데이터 서버 캐시 + 즉시 무효화

- `apiGet`의 서버 측 호출을 Next 데이터 캐시에 저장합니다(태그 `public-data`, 안전망 TTL 5분).
- 로그인 사용자의 모든 쓰기는 BFF의 `forwardWithSession`을 지나갑니다. 여기서 쓰기가 성공하면 `revalidateTag(tag, { expire: 0 })`로 캐시를 전부 비웁니다. 회원가입도 같습니다.
- `expire: 0`이라 다음 조회는 옛 데이터를 주지 않고 새로 받아올 때까지 기다립니다. 공개 범위를 비공개로 바꾸면 다음 조회부터 바로 사라집니다.
- 브라우저의 `/api/profiles/*` 읽기는 rewrite 대신 Route Handler(`app/api/profiles/[...path]/route.ts`)가 같은 캐시에서 답합니다.
- 자유 검색(`/api/discovery/search`)은 키가 무한해서 캐시하지 않습니다. 로그인 전용 읽기(`/api/private/*`, `auth/me`)도 캐시하지 않습니다.
- 200 응답만 저장되므로 없는 프로필이나 비공개 여행의 404는 캐시되지 않습니다.

지연 프록시(요청당 +300ms) 기준 결과:

| 페이지 (비로그인) | 캐시 전 | 캐시 후 | 백엔드 호출 |
| --- | --- | --- | --- |
| `/traveler` 프로필 | 0.49s | 0.03s | 4 → 0 |
| `/traveler/travel/1` 여행 상세 | 0.36s | 0.02s | 2 → 0 |
| `/discover` 둘러보기 | 0.35s | 0.01s | 1 → 0 |
| `/api/profiles/traveler/travels` (랜딩 지구본) | 백엔드 직행 | 0.01s | 1 → 0 |

무효화 검증(익명 방문자 시점에서 확인):

| 동작 | 다음 조회 결과 |
| --- | --- |
| 공개 여행 생성 | 프로필과 목록에 바로 표시 |
| 제목 수정 | 옛 제목 사라지고 새 제목 표시 |
| 비공개 전환 | 목록에서 사라지고 상세는 "페이지를 찾을 수 없습니다" |

### 2. DB 커넥션 유휴 시간 60초 → 4분

- `application-prod.yaml`의 `idle-timeout` 기본값을 240초로 올렸습니다.
- Neon의 절전 기준(5분)보다 짧고, 쿼리를 보내지 않는 유휴 커넥션은 절전을 막지 않습니다. 컴퓨트 시간은 늘지 않습니다.
- **주의:** Render 대시보드에 `DB_IDLE_TIMEOUT_MS=60000`이 직접 설정돼 있으면 그 값이 우선합니다. 그 변수를 지우거나 `240000`으로 바꿔야 적용됩니다.

### 3. 백엔드 gzip 압축

- `server.compression`을 켰습니다(JSON, 1KB 이상).
- 여행 목록 45,235B → 9,600B, 국가 11,868B → 2,905B.

## 코드로 해결되지 않는 부분 (권장)

효과가 큰 순서입니다.

1. **리전 맞추기.** Vercel 함수, Render, Neon을 같은 리전에 두세요. 로그인 페이지는 캐시할 수 없어서 왕복 지연이 그대로 남습니다. Vercel 프로젝트 설정의 Function Region을 Render 리전과 맞추는 것만으로도 차이가 큽니다.
2. **Render 유료 플랜(월 $7).** 무료 인스턴스는 0.1 CPU라 JVM이 느리고, 절전에서 깨는 데 수십 초가 걸립니다. 체감 속도에 가장 큰 영향을 주는 단일 요인입니다.
3. **Neon 절전.** 유료 플랜에서는 끌 수 있습니다. 무료에서는 5분 뒤 첫 쿼리가 0.5~수 초 느립니다.

## 이번에 하지 않은 것

- 로그인 화면(내 여행, 편집)의 백엔드 호출 합치기: 페이지당 2~4회가 이미 병렬이고, 합치려면 백엔드 API를 새로 만들어야 합니다.
- 다른 사람 프로필을 볼 때 팔로우·차단 상태 조회가 한 단계 늦게 시작하는 워터폴: 앞당기면 내 프로필을 볼 때 불필요한 호출이 2회 생겨 보류했습니다.
- 지구본 번들(three.js 1.6MB): 이미 지연 로딩이고 랜딩은 정적 페이지입니다.
